# TabMesh — Domain Language

## Glossary

### Core Architecture

- **Tab Coordinator**: The core abstraction. A hub-and-spoke event system that multiplexes a single backend transport across multiple browser tabs within the same origin. The hub is a SharedWorker (primary) or an elected Leader tab (fallback). Not a true mesh topology.
- **Hub Interface**: The abstraction boundary between TabMesh and the hub implementation. Both SharedWorker and Elected Leader implement the same interface. TabMesh code above this boundary is shared; only the hub implementation differs.
- **Same-Origin Constraint**: TabMesh coordinates tabs within the same origin (same protocol, host, and port). It does not coordinate across subdomains (`app.example.com` vs `admin.example.com`), browser profiles, incognito windows, or different browsers. This is a browser platform constraint, not a TabMesh limitation.

### Hub Implementations

- **Hub (SharedWorker) — Primary Mode**: A single SharedWorker instance shared across all tabs of the same origin. Holds the Transport connection, drains the Outbox, and relays events between tabs via MessagePort. Eliminates leader election, split-brain, and interregnum by design.
- **Hub (Elected Leader) — Fallback Mode**: For browsers without SharedWorker. One browser tab is elected Leader via Web Locks API (or BroadcastChannel/IndexedDB heartbeat). The Leader holds the Transport and relays events via BroadcastChannel. Subject to leader election, split-brain, and interregnum — mitigated by the Event Outbox. Has more edge cases around tab throttling and split-brain than primary mode.
- **Degraded Mode**: When IndexedDB is also unavailable. Falls back to an in-memory queue. The API surface is identical but durability is weakened — events survive within the tab session but not across tab closes or crashes. `mesh.start()` emits a `storage.degraded` system event and logs a console warning. Service Worker handoff is disabled.

#### Browser Support Matrix

| Environment | Default Mode |
|---|---|
| Desktop Chrome / Edge / Firefox / Safari | SharedWorker Hub |
| Safari iOS 16+ | SharedWorker Hub |
| Chrome Android | BroadcastChannel fallback |
| Samsung Internet | BroadcastChannel fallback |
| Legacy browsers | IndexedDB / degraded fallback |

### SharedWorker Details

- **Worker Identity**: SharedWorkers are identified by script URL + name. To avoid deployment edge cases where old and new tabs attach to different workers, use a stable URL (`/tabmesh-worker.js`) and a namespaced name (`tabmesh:{channelName}`). Protocol versioning happens inside messages, not via the script URL.
- **Protocol Versioning**: The Hub and tabs exchange a `protocolVersion` field in their handshake. If a tab connects with an incompatible protocol version, the Hub rejects it with an actionable error. This handles rolling deployments where old and new tabs coexist.
- **Worker Lifetime**: A SharedWorker stays alive while at least one connected browsing context remains alive. It is NOT a background sync engine. Background delivery after all tabs close requires the optional Service Worker integration and is browser-dependent.
- **Port Health Tracking**: The Hub maintains a registry of connected ports (`Map<tabId, { port, lastSeenAt, visibilityState }>`). Tabs send periodic `port.ping` heartbeats; the Hub responds with `port.pong`. Dead tabs (crash, BFCache, mobile suspension) are detected by stale `lastSeenAt` and their ports are cleaned up. Tabs also report lifecycle changes (`pagehide`, `pageshow`, `visibilitychange`, `freeze`, `resume`) to the Hub.

### Events

- **Event**: The core data unit. Has `type` (free-form string), `payload` (arbitrary data), `priority` (number, default 0), and `ttl` (milliseconds, optional). Events are not commands or queries — they represent something that happened or needs to be communicated.
- **Event Type**: A free-form string identifying the kind of event. Dot-notation (e.g., `chat.message`, `auth.logout`) is a documented convention, not enforced.
- **Priority**: Controls send order only. Higher-priority events are drained from the Outbox before lower-priority ones. Does not affect TTL or delivery guarantees. Default: 0.
- **TTL (Time-To-Live)**: Relative to the event's creation time. An event created at time T with a TTL of 24h expires at T+24h, regardless of when the Hub processes it. Expired events are discarded during Outbox drain.
- **Event ID**: Format `{tabId}-{monotonicCounter}`. Cheap to generate, globally unique within a channel, and sortable per-tab. Generated by the sending tab at creation time.
- **Event Source**: Every event delivered to a `mesh.on()` handler carries a `source` field: `'local'` (originated from this TabMesh client) or `'remote'` (originated outside this client — another tab or the backend). Handlers receive events from both sources by default. Users who need to skip local echoes filter with `if (event.source === 'local') return`. Internal metadata (`event.meta.internalSource`: `'port'` | `'broadcast'` | `'transport'`) is available for debugging but not part of the public API.
- **Inbound Event Flow**: Backend → Transport → Hub → all tabs. The Hub does not write inbound events to the Outbox (persistence is the backend's responsibility). No replay buffer for late-joining tabs — new tabs start with a clean slate and fetch historical state from the backend if needed.
- **Inbound vs Outbound Events**: Both share the same `type`/`payload` shape. Outbound events additionally carry `priority`, `ttl`, and an Event ID (generated by the sending tab). Inbound events pass through as-is without these fields.

### Outbox & Delivery

- **Event Outbox**: An IndexedDB-backed durable queue for outbound events.
- **Send Path (Primary — SharedWorker)**: Tab → MessagePort → Hub → IndexedDB Outbox → Transport → backend. The Hub owns all Outbox writes. Tabs do not write to IndexedDB directly. The Hub batches writes (~50ms window) and flushes in a single IndexedDB transaction.
- **Send Path (Fallback — Elected Leader)**: Tab → IndexedDB Outbox → BroadcastChannel notification → Leader → Transport → backend. Tabs write to the Outbox directly (write-through), then notify the Leader via BroadcastChannel. The Leader drains and delivers.
- **Delivery Status**: Each event in the Outbox carries a status: `pending` → `delivered`. The Hub marks events as `delivered` after successful Transport send (or after successful distribution to tabs in transport-less mode). Stale `pending` events are picked up when a new Hub starts.
- **Outbox Drain**: Only the Hub reads from the Outbox. Single reader avoids IndexedDB contention and deduplication complexity. The Hub reads all `pending` events, sends them via Transport (if configured), distributes them to other tabs, and marks them `delivered`.
- **Drain Trigger**: Notification-driven, not polling. In primary mode, tabs notify the Hub via MessagePort. In fallback mode, tabs post an `outbox.flush` signal on BroadcastChannel. The Hub drains immediately. Zero overhead when idle. On Hub startup, a catch-up drain picks up any stale events.
- **Outbox Cleanup**: Piggybacked on the drain cycle. When the Hub drains the Outbox, it deletes previously-delivered events and TTL-expired pending events in the same IndexedDB transaction. No extra timers or I/O passes. `mesh.stop()` also performs a cleanup pass for the idle edge case where no new events trigger a drain.
- **Send Semantics**: `mesh.send()` is "fire and persist." The promise resolves when the Hub acknowledges receipt (primary) or the Outbox write succeeds (fallback). It does not wait for backend delivery. The promise rejects only if the write/handoff fails (e.g., storage full, Hub unreachable).
- **Server ACK**: By default, the Hub marks events `delivered` after `Transport.send()` completes. This does not prove backend processing. For users who need confirmed delivery, a post-v1 `ackMode: 'server'` option will hold events as `pending` until the backend sends an explicit acknowledgment message.

### Transport

- **Transport**: A pluggable backend connection adapter (WebSocket, SSE, long-poll). Only the Hub opens a Transport.
- **Transport Interface**: A thin adapter with a minimal contract: `connect()`, `disconnect()`, `send(data: string)`, and event callbacks (`onMessage`, `onDisconnect`, `onError`). Transports are dumb pipes — they never see structured Event objects, only serialized strings.
- **Reconnection**: Owned by the Hub, not the Transport. When a Transport disconnects, the Hub runs retry logic (configurable maxAttempts, backoff) and calls `connect()` again. All Transport adapters get consistent reconnection behavior for free.
- **Serialization**: TabMesh serializes Events to JSON by default before passing to `Transport.send()`. A `serializer` option on TabMeshConfig allows swapping in custom formats (e.g., MessagePack) post-v1. The Transport only handles raw strings.
- **Transport-less Mode**: A TabMesh instance without a Transport is valid. It functions as a durable, priority-aware cross-tab event system. The Hub drains the Outbox and marks events `delivered` after successful distribution to other tabs. When a Transport is configured, the Hub additionally forwards events through it before marking them `delivered`.
- **One Transport Per Mesh**: A mesh has at most one Transport. No routing layer. Users needing multiple backends can: (1) use multiple meshes with separate channel names, (2) use a backend gateway, or (3) build a custom Transport adapter that internally multiplexes connections.

### Service Worker

- **Service Worker Handoff**: The Hub owns the Event Outbox during normal operation. When the Hub dies (all tabs close), the Service Worker takes over Outbox draining via Background Sync. The SW's `sync` handler checks for stale `pending` events as a fallback since `beforeunload` is unreliable on mobile. Background delivery after all tabs close is browser-dependent and best-effort.

### Session & Auth

- **Session Scoping**: The `channelName` should incorporate session identity to prevent cross-session event leakage. Recommended pattern: `channelName: 'app:{tenantId}:{userId}'` or use `mesh.setSession({ userId, tenantId, sessionId })`. On logout, the app must: `mesh.clearOutbox()` → `mesh.disconnectTransport()` → `mesh.broadcast({ type: 'auth.logout' })` → `mesh.stop()`. This prevents old events from being sent under a new session.

### Lifecycle

- **Lifecycle — `start()`**: Async. Starts the Hub (SharedWorker or fallback election), connects the Transport (if configured), and registers the Service Worker (if configured). Resolves successfully even if the Transport fails — the mesh operates in transport-less mode and retries the connection in the background.
- **Pre-start sends**: Calling `mesh.send()` before `start()` does not throw. Events are buffered and drained when `start()` completes.
- **Lifecycle — `stop()`**: Disconnects from the Hub, flushes pending Outbox events (with a short timeout). Does not clear the Outbox — stale events expire via TTL.
- **System Events**: TabMesh emits internal events for lifecycle changes. Hub and Transport events are distinct:
  - `hub.connected` — tab connected to the Hub (SharedWorker or elected Leader)
  - `hub.disconnected` — tab lost contact with the Hub
  - `transport.connected` — Hub connected to the backend
  - `transport.disconnected` — backend transport disconnected
  - `transport.reconnecting` — Hub is retrying the Transport connection
  - `transport.error` — Transport-level error
  - `event.delivery.failed` — Hub exhausted retries for a specific event
  - `storage.degraded` — IndexedDB unavailable, using in-memory fallback

### Identity

- **Tab ID**: 8 hex characters generated from `crypto.getRandomValues()`, stored in `sessionStorage`. Survives page reloads (same tab session), regenerated when the tab is closed and reopened. Used in Event IDs (`{tabId}-{counter}`).
- **Channel Name**: An app-level identifier that scopes the SharedWorker, IndexedDB database, and sessionStorage keys (or BroadcastChannel and leader lock in fallback mode). One mesh per app is the intended usage. Multiple `channelName` values in the same origin work (each creates an independent mesh) but are an advanced pattern — they multiply backend connections and Hub instances.

### Error Handling

- **Error Model**: Split into two categories. (1) **Synchronous throws** (`TabMeshError`) for programmer mistakes: calling methods after `stop()`, invalid config. (2) **System events** for runtime conditions: `transport.error`, `transport.disconnected`, `event.delivery.failed`, `storage.degraded`. Apps react via `mesh.on()`, not try/catch.

### React Integration

- **React Integration Pattern**: Hooks accept an optional TabMesh instance argument. If omitted, they fall back to React context (`<TabMeshProvider>`). The documented default is direct instance passing (singleton module import) — idiomatic for a singleton-by-nature library. Context provider is shipped as an escape hatch for testing, Storybook, or multi-app-per-page scenarios.

### Fallback Mode Details

- **Leader Election Strategy**: Layered fallback, selected once at startup based on browser capabilities. Only one strategy runs at a time. (1) **Web Locks API** — sub-50ms failover. (2) **BroadcastChannel heartbeat** — Leader broadcasts every 500ms; Followers declare candidacy after 1.5s silence. ~1-2s failover. (3) **IndexedDB heartbeat** — Leader writes a timestamp every 2s; tabs race to claim leadership if stale for >5s. ~2-5s failover.
- **Split-Brain Resolution**: When a tab becomes Leader, it broadcasts a `leader.elected` event with its tab ID and a monotonic term number. If a tab receives this and also believes it is Leader, the tab with the lower term (or lower tab ID as tiebreaker) demotes itself and closes its Transport. Backends should treat events idempotently. No fencing tokens — this preserves backend-agnostic design.

## Scope

### v1
- SharedWorker Hub (primary)
- Elected Leader Hub (fallback)
- Event Outbox (IndexedDB, write-through, batched)
- Transport Manager + WebSocket adapter
- Core TabMesh class orchestrating the above
- Service Worker integration (offline/background sync with handoff model)
- React hooks (`@tabmesh/react`)
- TypeScript types, tree-shaking, ESM/CJS

### Post-v1
- Server ACK mode (`ackMode: 'server'`)
- SSE and long-poll transport adapters
- DevTools browser extension
- Web Worker for batching/compression
- Vue composables, Svelte stores
- Interactive playground
- Migration guides, documentation website
- MessagePack compression
